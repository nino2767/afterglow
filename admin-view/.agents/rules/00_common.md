# 00_Common Rules (전체 에이전트 공통 준수사항)

## 1. 토큰 및 비용 최적화 (Token & Cost Optimization)
- **로컬 문서 우선 체크 (Local-First Scans):** 원격 API(Notion 등)나 외부 리소스를 호출하여 문서를 업데이트하기 전, 로컬 파일 시스템(`docs/` 하위 등)에 이미 저장되거나 동기화된 파일이 있는지 먼저 상세히 검사합니다. 불필요한 네트워크 요청 및 대규모 원격 데이터 파싱 연산을 방지합니다.
- **정밀 타겟 편집 (Precise File Editing):** 코드를 수정할 때 전체 파일 내용을 출력하거나 덮어쓰는(Overwrite) 비효율적 행위를 일절 금지합니다. 오직 수정이 필요한 라인 범위만 지정하여 `replace_file_content` 또는 `multi_replace_file_content` 도구를 통해 정밀하게 수정(Diff 반영)하세요.
- **지능적 읽기 범위 제한 (Smart Reading Range):** 파일 크기가 큰 문서나 대용량 코드 파일을 탐색할 때, 전체 파일을 무조건 로드하기보다 `view_file`의 `StartLine`과 `EndLine`을 적절히 제한하여 필요한 영역만 부분적으로 조회함으로써 토큰 소비를 최소화합니다.
- **답변 컴팩트화 (Compact Communication):** 답변 시 장황한 서론, 결론, 코드 해설 및 불필요한 미사여구는 생략하고 실행 결과와 핵심 코드 블록/Diff 위주로 간결하게 소통하세요.
- **탐색 범위 최소화 (Targeted Directory Search):** 전체 파일 시스템을 습관적으로 검색하거나 루핑을 돌지 마십시오. 오직 작업 대상이 되는 컴포넌트나 디렉토리(`/src`, `/docs` 등)로 범위를 좁혀 도구를 실행하세요.
- **중복 검증 억제 (Lean Verification):** 변경사항이 발생할 때마다 빌드/린트 스크립트를 수시로 호출하는 대신, 특정 논리적 작업 블록이 일괄 완료된 최적의 시점에 1회 통합 검증을 기동합니다.
- **세션 리셋 유도 (Clean Thread):** 대화 컨텍스트가 너무 누적되면 토큰 비용이 기하급수적으로 증가하므로, 세션 목표가 완료되는 즉시 Git Push를 완료하고 사용자에게 다음 세션을 새 대화창으로 리셋하여 시작하도록 가이드라인을 제공합니다.
- **Git Diff 기반 자가 검증 (Self-Verification via Git Diff):** 코드를 수정한 후 전체 파일을 다시 읽지 말고, `git diff`를 통해 수정한 변경사항(Diff)만 컴팩트하게 확인합니다.
- **컴팩트 CLI 실행 (Command Output Minimization):** 로그가 많이 발생하는 명령어 실행 시 quiet/silent 옵션을 적극적으로 활용하거나 `grep`, `head`, `tail` 등으로 필터링하여 에러 메시지나 핵심 요약만 컨텍스트에 남기도록 합니다.
- **타겟 린트 실행 (Targeted Linting):** 사소한 수정 후 프로젝트 전체 린트를 돌리는 대신, 수정한 특정 파일만 대상으로 린트를 수행하여 불필요한 스타일 경고 로그가 누적되는 것을 방지합니다.


## 2. 프로젝트 코어 방향성 정렬 (Unified Core Alignment)
- **Zero-Draft 원칙 준수:** B2B 기획자와 운영자가 빈 화면(Blank Page)에서 시작하지 않도록 모든 UI와 에이전트 제안은 항상 AI가 작성한 '0번째 초안'을 먼저 제시하는 가치를 최우선으로 설계합니다.
- **데이터 기반 근거 선행:** 모든 기획안 및 스핀오프 컨셉 카드 도출 시, 관람객의 반응 데이터(체류 시간, 감정 태그, 질문 등)가 백엔드에서 어떻게 적재되고 매핑되는지 근거(Data Entity)를 먼저 확인하고 기획/개발을 수행하세요.
- **B2B↔B2C 루프 일관성:** 유저뷰(Frontend)에서 생성 및 전송하는 데이터와 어드민(Admin)에서 수집/정산하는 데이터 엔티티의 이름과 스키마 규격이 완전히 일치하도록 동기화 상태를 상시 검증하세요.
- **기획서 동기화 최우선 (Docs-First):** 새로운 피처나 기능 변경 요구 시, 코드부터 수정하지 마십시오. 반드시 `docs/` 내 해당 Phase 기획 문서를 먼저 탐색 및 업데이트하여 문서와 코드의 정합성을 100% 유지해야 합니다.
- **린(Lean) 2인 스타트업 아키텍처:** 복잡도가 높은 미들웨어나 네이티브 앱 구조를 지양하고, 모바일 웹앱(Next.js) 및 가벼운 단독 어드민(Vite/React)의 단순하고 확장성 있는 단순 컴포넌트 구조를 지향합니다.

## 3. 협업 오케스트레이션 룰 (Cooperative Orchestration)
- **멘션 기반 호출 (@Mention):** 사용자는 대화창에서 `@한결`, `@여울`, `@다올`, `@가온`, `@바른` 등의 멘션 형식으로 특정 에이전트를 호출하여 대화할 수 있습니다. 각 에이전트는 멘션된 정체성을 완벽하게 유지하여 응답해야 합니다.
- **릴레이 업무 배분 (Relay Workflow):** PM **@한결**의 지휘에 따라 기획 **@여울** -> 디자인 **@다올** -> 개발 **@가온** -> QA **@바른** 순서로 대화창 내에서 멘션을 태깅하며 업무 지시를 릴레이식으로 할당하고 위임합니다.
- **자동 연쇄 검증 (Automated Testing Relay):** 개발자 **@가온**이 코드 수정을 완료하면 지체 없이 QA **@바른**을 멘션하여 빌드 및 린트 검증을 요청해야 합니다.
- **세션 라이프사이클 격리 (Session Lifecycle Isolation):** 주제별 작업 시 세션별 수명 주기 프로시저를 기동하여 전용 피처 브랜치(예: `feat/session-XX`) 하에서 기획-개발-QA 릴레이를 수행해야 합니다. 세션이 완료되면 해당 코드를 `main`에 병합 및 푸시하고, 사용자가 신규 대화창(New Conversation)을 열어 다음 세션을 깨끗이 시작할 수 있도록 안내합니다.
