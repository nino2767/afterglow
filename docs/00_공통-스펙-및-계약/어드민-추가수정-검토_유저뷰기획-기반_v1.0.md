## 0. 검토 전 반드시 확인할 것 (⚠️ 2건)

### 0-1. ⚠️ 코드 바인딩 상태가 문서 기록과 불일치

관제탑(진행 현황 로그)에는 "③ 어드민 대조·수정 (ConceptBot·Monitor·Report SSOT 바인딩) ✅ 완료 — repo 반영 완료"로 기록돼 있으나, **admin repo `main` 브랜치의 실제 코드를 확인한 결과 바인딩이 반영되어 있지 않음.**

| 확인 항목 | main 코드 현황 |
|---|---|
| ConceptBot.jsx | 여전히 구버전 `tag`("체험형/기술형/휴식형") A/B/C 하드코딩. `concept_type` enum 6종 미사용 |
| Monitor / Report / 전체 src | `concept_type`, `open_solo`, `SPINOFF_ZONE`, `invite.redeemed`, `landing_viewed`, `link_clicked`, `axis` — **전부 검색 결과 0건** |
| 최근 커밋 | `docs: 데이터 계약 SSOT v1.2 동기화 적용` — 문서 동기화만 확인됨 |

→ **해석 후보**: (a) 바인딩 작업이 별도 브랜치에 있고 아직 main 미머지, (b) "완료"가 문서 레벨 동기화를 의미. 어느 쪽인지 확인 후, 미머지면 이번 어드민 개발의 **0순위 작업은 SSOT v1.1 §후속 큐(ConceptBot·Monitor·Report 바인딩) 자체**가 됨. 아래 항목들은 그 바인딩 위에 얹히는 델타임.

### 0-2. 🔴 SSOT ↔ 「데이터 수집 방식 및 정보」 충돌 (기존 보류 건)

감정 모델(8축 vs 5카테고리) · 세그먼트(4종 vs 5종) · 이벤트 단위(퍼널 6단계 vs 세분 행동로그) 충돌이 병합 보류 상태. **본 문서의 §3(Monitor)·§4(Report) 항목은 전부 SSOT v1.2를 기준으로 작성**했으며, 병합 결정이 SSOT 반대편으로 나면 해당 절은 재검토 필요. 유저뷰와 동일하게 **어드민도 데이터 표시부(감정·세그먼트·이벤트 지표) 코딩은 충돌 해결 전까지 보류, UI 골격부터** 진행 권장.

## 1. 신규 개념 3가지 — 어드민에 처음 등장하는 것

유저뷰 기획에서 새로 확정됐지만 어드민 기획·코드 양쪽에 아직 대응물이 없는 개념. 이번 수정의 핵심 델타.

| # | 개념 | 출처 | 어드민 영향 | 우선순위 |
|---|---|---|---|---|
| N1 | **계정 모델 (ACCOUNT)** — 게스트 우선 + 카카오/이메일, VISITOR 1:N 병합 | SSOT v1.2 §7, 화면0/7~10 | 관람객 카운트 정의 변경, 재방문·회원전환 지표, 알림 발송 트리거 (§4·§6) | P1 |
| N2 | **팝업 상태머신** — `planning→ready→open_concurrent→open_solo→closed→archived` | 운영정책 §1 | 스핀오프 기획 화면에 상태 전이 UI + 자동 전이 + 저장 시 검증 로직 (§2) | **P0** |
| N3 | **열람 모드** — 계정 모드에서 화면4/5 재열람, 이벤트 미발화 | IA §2, 화면4 §4-1·화면5 §3-1 | 어드민 화면 신규 없음. 단 지표 정의에 "재열람은 퍼널 미집계" 명시 필요 (§4) | P1 (정의만) |

## 2. 스핀오프 기획 (ConceptBot / Phase 4) — 변경 최대

### 2-1. 팝업 오픈·종료 설정 + 검증 로직 🆕 **P0**

운영정책 §1이 어드민에 명시적으로 요구하는 사항. 현재 Phase 4 문서·코드 어디에도 없음.

- 팝업 오픈일/종료일 설정 필드 (오픈 = 본전시 오픈~기간 중 임의 시점)
- **저장 시 강제 검증: `main.end + 21d ≥ spinoff.end`** (단독 연장 21일 상한)
- 파일럿 개설 조건 체크리스트(본전시 잔여 ≥ 4주 등, v3.0 §8) — 개설 시 확인 UI로 노출 권장
- ❓ 미결정 의존: 최소 리드타임 2주 / MVP 무료 입장 — 이 2건이 확정돼야 설정 필드 스펙이 닫힘 (운영정책 §6)

### 2-2. 상태머신 전이 UI 🆕 **P0**

- 상태 뱃지 + 수동 전이 버튼 (`planning→ready→open…→closed`)
- 자동 전이: main 종료일 도달 시 `open_concurrent→open_solo` (날짜 기반)
- `closed` 전이 시 부수효과: 미사용 초대장 자동 만료 + 유저뷰 랜딩이 종료 화면으로 전환됨을 안내

### 2-3. SPINOFF_ZONE 산출·관리 **P0**

SSOT v1.1 §6 + 화면6이 소비. ConceptBot 공간 구성안이 자유 텍스트가 아니라 **ZONE 구조로 산출**되어야 함.

- 존 3~5개 (운영정책 §4 — 본전시 핵심 작품 3~5개와 대칭)
- 존별 필드: `concept_type`(팝업 대표 유형과 다를 수 있음), title, experience_desc, **docent_script**(화면6 존 해설 원천), linked_md_ids[], **존 QR 생성**(Phase 1 QR 엔진 재사용)

### 2-4. 랜딩 콘텐츠 세팅 🆕 P1

화면5가 읽는 데이터인데 현재 어드민에 입력처가 불명확. Phase 4 산출물 확정 후 편집하는 세팅 뷰 필요.

- concept_type별 키 비주얼 / MD 라인업(이름·가격·이미지·한줄 설명) / **외부 커머스·예약 링크**(MVP 자체결제 없음) / 팝업 위치·지도·운영기간
- **웰컴 혜택 설정** 🆕 — 셀프 체크인 보상(화면5 ⑤). 운영자 설정제, default 제안 "굿즈 구매 시 스티커". 혜택 바코드 1회 사용·초대장과 동일 만료
- **default concept 지정** 🆕 — 데이터 빈약/비온보딩 관람객용 초대장 fallback (화면4 §5). 운영자 지정 1종

### 2-5. 코드 정합 (0-1 후속) **P0**

- `CONCEPTS`의 `tag` → `concept_type` enum 6종(story/sensory/archive/community/role/time) 교체 — SSOT v1.1 §5로 이미 enum은 확정된 상태 (6유형 vs 6모드 논쟁은 SSOT가 mode-spec Layer 1 쪽으로 정리함. Phase 4 문서의 구 6유형 표는 "관람객 욕구 레이어" 참고자료로 지위 정리 필요)
- 각 컨셉 카드에 Bridge 트리거 문구 필드 — 화면4 personalized_copy 톤의 원천이므로 유저뷰 카피와 한 소스 유지

## 3. 관람 모니터 (Monitor / Phase 3)

### 3-1. 지표 정의 반영 (화면2·3 확정 스펙) P1

| 유저뷰 확정 사항 | Monitor 반영 |
|---|---|
| `dwell_sec` = 카드 오픈~다음 스캔/이탈, 백그라운드 일시정지 | 체류시간 지표 정의 각주 통일 |

| 감정 퀵반응(카드)과 대화 감정칩 — **동일 가중** (화면2 결정) | 감정 집계 시 소스 구분 없이 합산 (파일럿 후 튜닝 여지 주석) |

### 3-2. 감정어 승인 큐 (`pending_review`) 🆕 P1

화면3 §4-3: 전시 EMOTION_LEAF에 없는 감정어는 `pending_review` 적재 → **운영자 승인 후 active 전환**. 어드민에 대응 UI가 전혀 없음. Phase 2(AI 학습) 또는 Phase 3에 승인 큐 목록 + 승인/기각 액션 신규. (승인 즉시 관람객 화면 칩 노출에 반영되는 실시간성 여부는 결정 포인트)

### 3-3. 스핀오프 존 뷰 P1

`spinoff.session_start / zone_viewed / curator_chat` 기반 존별 인기·체류 — 전시 스위처에서 spinoff 선택 시 Monitor가 존 단위로 전환. (0-1 바인딩 큐에 이미 포함된 항목의 재확인)

## 4. 성과 리포트 (Report / Phase 5·6)

### 4-1. 퍼널 6단계 + 집계 창 **P0** (지표 정의)

- 퍼널: `session.start → curator.chat_start → invite.issued → invite.landing_viewed → invite.redeemed → purchase.link_clicked`
- **전환율 20% = 4단계/1단계**, 집계 창 = main 오픈 ~ **spinoff closed** (단독 구간 포함, 운영정책 §5)
- `invite.redeemed`의 MVP 검증 방식 = self_checkin — 리포트에 검증 수준 명시 (v2: 현장 QR)

### 4-2. C경로 분리 지표 🆕 P1

화면5 §2: 일반 유입은 `landing.organic_viewed`로 **퍼널 밖 참고 지표**. 단독 운영 기간(open_solo)의 "놓친 사람 유입" 성과를 보여주는 별도 카드 — 퍼널 20%와 섞이면 안 됨.

### 4-3. 열람 모드 미집계 원칙 P1

재열람(화면8/9→4/5)은 이벤트 미발화 — 리포트 각주로 "재열람은 CTR·전환에 미포함" 명시. 반대로 열람 모드에서의 `purchase.link_clicked`는 **유효 발화**(재구매) — 구매 지표에는 포함됨. 이 비대칭을 지표 정의서에 정확히.

### 4-4. 계정 지표 (N1) — 범위 결정 필요 ❓ P1~P2

SSOT v1.2 §8은 "회원 전환율·재방문율 = v2 후보(⬜)"로 뒀으나, 유저뷰가 계정을 MVP IN으로 승격한 만큼 어드민도 최소 노출 검토 여지:

| 안 | 내용 |
|---|---|
| A. v2 유지 (현행) | MVP 리포트는 세션 기준만. 계정 데이터는 쌓기만 함 |
| B. 최소 노출 (제안) | `account.signup / visitor_merged` 카운트 2개만 리포트에 추가 — 파일럿에서 "로그인 도입이 효과 있었나" 판정용. 재방문율·CRM 뷰는 v2 |

관람객 카운트 정의도 함께: Monitor/Report의 "관람객 수"는 **visitor(기기) 기준 유지**, account는 별도 지표로 분리 (혼용 금지).

## 6. 신규 기능 후보 — 오픈 알림 발송 🆕 ❓ 결정 필요

유저뷰에 opt-in 접점이 3곳 생겼는데(화면4 "오픈 알림 받기" · 화면5 오픈 전 opt-in · 화면7 전시별 알림 토글), **발송하는 쪽 기능이 어드민 어디에도 없음.**

- 트리거: 상태머신 `ready → open_*` 전이 시 opt-in 사용자에게 알림 (§2-2와 결합하면 자동화 가능)
- MVP 판단 필요: (a) MVP IN — 전이 시 발송 버튼 1개 수준의 최소 구현 / (b) MVP OUT — opt-in 데이터만 쌓고 발송은 수동(외부 툴). 웹앱이라 채널도 미정(알림톡? 이메일?) — **채널 결정이 선행**이라 (b)로 시작이 현실적
- 어느 쪽이든 opt-in 리스트 조회(카운트+내보내기)는 P1로 필요 — 없으면 수동 발송조차 불가

## 7. 영향 없음 확인 (변경 불필요)

- **고객사 관리 어드민(super)**: 계정·계약·RS 도메인 — 이번 유저뷰 델타와 무관 (기존 매핑 결론 유지)
- **정산 관리**: 데이터 구조 영향 없음. 단, 운영자 vs super 소속 정리 이슈는 별건으로 계속 오픈
- **대시보드(overview)**: 전시 목록 진입점 역할 그대로. 상태머신 뱃지(§2-2)를 카드에 노출하면 좋으나 필수 아님(P2)

## 8. 착수 순서 제안

1. **§0-1 확인** — 바인딩 코드가 브랜치에 있는지. 없으면 SSOT 바인딩(ConceptBot·Monitor·Report)이 Sprint 1
2. **P0 묶음** — 상태머신+검증(§2-1·2-2), SPINOFF_ZONE 산출(§2-3), 퍼널 정의(§4-1). 전부 스핀오프 기획/리포트 화면에 집중되고 유저뷰 화면5·6 개발과 직결
3. **P1 묶음** — Phase 1·2 필드 델타(§5), 승인 큐(§3-2), C경로 지표(§4-2), 랜딩 세팅(§2-4)
4. **결정 대기** — 리드타임·입장료(운영정책 ❓), 계정 지표 범위(§4-4 A/B), 알림 발송 MVP 여부(§6), SSOT 충돌 병합(§0-2)
